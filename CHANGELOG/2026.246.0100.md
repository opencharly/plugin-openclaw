# 2026.246.0100 — feat: openclaw check verb plugin

## Summary

Adds the `openclaw:` check verb — an out-of-tree, out-of-process plugin that probes a
running [OpenClaw](https://openclaw.ai) 2.0 gateway. It is the probe half of OpenClaw
support in charly; the gateway itself is installed by
[`pod-openclaw`](https://github.com/opencharly/pod-openclaw).

The repo also carries a root `charly.yml` with a `discover:` block — the project
config that makes the repo's own candy actually gated by `charly box validate`
(without it a plugin repo is "project-less" and the stock CI step exits 0 on any
manifest; opencharly/charly#459).

7 methods, all read-only:

| Group | Methods |
|---|---|
| HTTP probes (host-side) | `health` (`/healthz` liveness) `ready` (`/readyz` readiness) `startup` (`/startupz` startup) |
| In-venue CLI | `status` (`openclaw status --all`) `models` (`openclaw models status`) `channels` (`openclaw channels status`) `version` (`openclaw --version`) |

No edit to `charly/` or `spec/` is needed: `checkVerbProviderBijection` explicitly allows
out-of-tree verbs, and `openclaw` collides with no authored `#Op` field.

### Why this is not the generic `http:` verb (R3)

`http:` already does URL + status + body/header matchers, and duplicating that would be
pointless. This verb exists for what `http:` structurally cannot do:

- **Endpoint resolution.** `cc.ResolveEndpoint` turns the in-venue gateway port into a
  host-reachable address, so one authored step works unchanged against a pod's published
  port and a VM's forwarded one.
- **Domain semantics.** Methods map to the gateway's real probe surface (the 2.0
  container-probe endpoints) and return real verdicts, with `json_path:` to assert one
  field rather than pattern-matching a JSON blob.
- **In-venue CLI.** The status/models/channels methods run the `openclaw` binary inside
  the venue over the reverse channel — `http:` cannot reach the gateway CLI at all.

### Design decisions worth reviewing

**1. HTTP probes run from the host, CLI methods run in-venue.** The openclaw gateway
binds to loopback and is relayed to the container interface by socat (the openclaw
candy's port_relay), so the host CAN reach the probe endpoints via the resolved
published port — unlike punktfunk's loopback-only management API, which forced in-venue
curl. The CLI methods (status/models/channels) need the `openclaw` binary, which only
exists in the venue, so they run over the reverse channel.

**2. All methods are read-only.** There are no mutating methods in this first cut —
channel login, model set, and other state-changing operations are a follow-up, and any
future mutating method must be `run:`-only per the punktfunk doctrine.

**3. The schema is self-contained.** `#OpenclawInput` references no base def, so it
compiles standalone (`cue exp gengotypes`) and splices onto the base at runtime.
