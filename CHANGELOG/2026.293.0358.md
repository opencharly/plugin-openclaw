# 2026.293.0358 — fix(skill): rename the check-verb skill to `openclaw-cmd` so the flat harness farm can bind both

## Summary

`openclaw` is claimed by two different skills in two different families, and both claims are correct:

| manifest | kind | `family:` | `owner:` | what it is |
|---|---|---|---|---|
| `layer-openclaw/box/openclaw/charly.yml` | box | `openclaw` | `openclaw` | the gateway **box** |
| `candy/plugin-openclaw/charly.yml` | plugin verb | `check` | `plugin-openclaw` | the `openclaw:` **check verb** |

The derived harness binding keys the farm `.dsh/skills/<name>` and drops the family, so it cannot hold both, and it refuses rather than silently binding one:

```
FAIL: corpus skill name collisions across families (a flat farm cannot bind both):
openclaw: check + openclaw
```

This renames the **check-verb skill id** to `openclaw-cmd`. The `openclaw:` check verb itself is unchanged — only the skill id moves, so `/charly-check:openclaw` becomes `/charly-check:openclaw-cmd`. The precedent is `charly-mcp-cmd`, created for exactly this shape: a command skill colliding with a box skill of the same name.

**Namespacing the farm by family was measured and rejected, not skipped.** `dsh-skill-filesystem`'s `discoverRoot` performs a single `readdir(root.path)` and reads `<entry>/SKILL.md` — depth 1 — and takes the skill's name from the parsed `SKILL.md` frontmatter (`skills.push({ name: parsed.name, … })`), not from the directory. A nested `.dsh/skills/<family>/<name>/` would therefore be invisible to discovery, and two files both declaring `name: openclaw` would still collide whatever their path. Renaming is the only fix available without changing DSH itself.
